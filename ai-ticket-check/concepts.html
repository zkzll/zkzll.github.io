AI/LLM 核心概念详解

CONCEPT DEEP DIVE — WITH PROJECT CONTEXT
1
ReAct 推理
Reasoning + Acting
WHAT IT IS
ReAct 是一种让大语言模型（LLM）交替进行「思考」和「行动」的推理范式。模型先思考当前该做什么（Thought），然后决定调用某个工具或执行某个动作（Action），观察到工具返回的结果后（Observation），再继续下一轮思考。如此循环，直到任务完成。
💡 通俗理解
想象你在查快递丢件。你先想一下应该先看物流轨迹（思考），然后打系统查一下轨迹（行动），看到结果发现卡在清关环节（观察），再想应该去查清关状态（思考），然后打系统查清关数据（行动）……这就是 ReAct 循环。AI 智查里的 Agent 就是这么工作的。
ReAct LOOP
Thought 思考
→
Action 行动
→
Observation 观察
↻ 循环直到任务完成（调用 finish_main_task）
📂 项目中的实现
CbsReactAgentFactory 创建 ReactAgent 实例，基于 Spring AI Alibaba 的 Graph 框架构建 ReAct 循环。
每轮循环产生两种节点：MODEL 节点（LLM 输出思考过程，流式推送 token）和 TOOL 节点（LLM 决定调用某个 MCP 工具，如 qctask_attribution_infer），执行结果作为下一轮 Observation 输入。
ThoughtProcessStrategy（12 种策略）控制不同业务域的思考方式——比如清关 Agent 会先想 HS Code 分类逻辑，揽收 Agent 会先想地址解析策略。
2
LLM Agent 框架
LangEngine / Spring AI / DashScope / CNAI Gateway
WHAT IT IS
LLM Agent 框架是构建 AI 智能体的基础设施层，它封装了与大模型交互的复杂性——包括调用模型、管理对话上下文、注册和调用工具、处理流式输出等。开发者只需关注业务逻辑，不需要自己处理 HTTP 请求、token 计算、重试等底层细节。
💡 通俗理解
如果把 LLM 比作大脑，Agent 框架就是身体的「神经系统」。大脑（LLM）负责思考和决策，神经系统（框架）负责把大脑的指令传递给手脚（工具），并把手脚的感知反馈给大脑。没有框架，你得手动拼凑一切；有了框架，你只需要告诉 Agent「去查这个工单」，它自己知道怎么调工具、怎么处理结果。
本项目涉及的框架层级
层级组件职责
应用框架LangEngine 1.2.2Agent 编排引擎，定义 Agent 的构建方式、工具注册、执行流程
AI 抽象层Spring AI 1.1.0统一 AI 基础设施接口：ChatModel（模型）、ToolCallback（工具）、VectorStore（向量库）
生态适配Spring AI Alibaba 1.1.2阿里生态适配：ReactAgent Graph 框架、DashScope ChatModel 实现
模型服务DashScope阿里云大模型服务平台，提供通义千问系列模型的 API 调用
网关CNAI Gateway AI集团统一 AI 网关，统一鉴权、限流、路由、模型版本管理
📂 项目中的协作关系
TicketCheckSkillsAgent 使用 LangEngine 构建 Agent → Agent 内部通过 Spring AI 的 ChatModel 接口调用 DashScope 模型 → 请求经过 CNAI Gateway 统一网关 → DashScope 返回推理结果 → Spring AI 将结果封装为 Flux<NodeOutput> 流式输出。开发者只需写 agent.stream(prompt, config) 一行代码即可驱动整个链路。
3
RAG
Retrieval-Augmented Generation · 检索增强生成
WHAT IT IS
RAG 是一种让 LLM 在回答问题前先「查阅资料」的技术。传统 LLM 只能依赖训练时记住的知识，对于企业内部业务规则、最新数据往往一无所知。RAG 的做法是：先把知识库文档向量化存储，当用户提问时，先从向量库中检索出最相关的知识片段，然后把这些片段注入 LLM 的上下文中，让 LLM 基于这些真实资料来回答。
💡 通俗理解
考试的时候开卷和闭卷的区别。LLM 本身是「闭卷考试」——它只知道训练时学过的东西。RAG 就是给它开卷，让它在回答前先翻一下「参考书」（企业知识库），这样回答就更准确、更有依据，不容易胡说八道（幻觉）。
用户提问
→
向量检索
→
相关知识片段
↓
LLM（问题 + 检索到的知识）→ 生成回答
📂 项目中的应用
cbaa-knowledge 模块中的 VectorStore 存储跨境物流的业务规则库（如各国海关申报规则、HS Code 分类标准、常见异常处理流程等）。Agent 推理时，先检索相关知识注入上下文，再让 LLM 基于这些真实规则进行归因推理和话术生成，显著提升回答准确性。
4
Memory 记忆体系
Short-term Memory & Long-term Memory
WHAT IT IS
LLM 本身是无状态的——每次对话它都不记得之前聊过什么。Memory 体系给 Agent 加上「记忆」能力，分为短期记忆和长期记忆两层。短期记忆维护当前对话的上下文窗口（最近 N 轮对话），让 Agent 能理解上下文连贯的对话。长期记忆跨会话持久存储关键信息（如用户偏好、历史处理模式），让 Agent 在下次遇到类似场景时能参考历史经验。
💡 通俗理解
短期记忆 = 你正在和同事讨论一个工单，你记得刚才聊的内容（当前对话窗口）。长期记忆 = 你记得上周处理过类似的清关异常工单，当时的归因结论和解决方式（跨会话经验积累）。没有记忆体系，Agent 每次对话都是从零开始，无法做到上下文连贯和经验复用。
📂 项目中的实现
DashScopeMemoryClient（短期记忆）— 管理当前对话的上下文窗口，维护 Agent 在 ReAct 循环中的 Thought / Action / Observation 历史，确保 LLM 能理解前后关联的推理链。

LongTermMemoryService（长期记忆）— 跨会话持久存储，记录用户/渠道的处理偏好、高频异常模式等。比如某个渠道的工单总是因为「申报价值不符」触发，长期记忆可以让 Agent 优先检查这个方向。
5
流式推理
Streaming Inference · SSE · Flux
WHAT IT IS
流式推理是指 LLM 生成回答时，不是一次性返回完整结果，而是一个 token 一个 token 地「流式」输出。就像打字一样，你能看到字一个一个蹦出来，而不是等很久然后突然出现一大段文字。这种方式大幅提升了用户体验——用户不需要等待整个推理过程结束，可以实时看到 Agent 的思考和行动过程。
💡 通俗理解
对比两种外卖体验：非流式 = 你点了外卖，等了 30 分钟，外卖一次性送到。流式 = 你在手机上看骑手实时位置，看着他一步步靠近，心里更踏实。流式推理让用户能实时看到 Agent 「在想什么」「在做什么」，而不是黑盒等待。
技术链路
DashScope 流式 API — 模型服务端逐 token 返回结果
Flux<NodeOutput> — Java Reactor 响应式流，每个 token 是一个事件
DashScopeStreamHelper — 封装流式调用细节（超时、重试、背压处理）
QcStreamingLogAppender — 订阅 Flux 事件流，实时写入 DB + 推送到 SSE
SSE (Server-Sent Events) — HTTP 长连接，服务端向浏览器单向推送数据，前端实时渲染
📂 项目中的双节点流式输出
MODEL 节点：LLM 流式输出思考过程（token by token）→ QcStreamingLogAppender 捕获 → SSE 推送到前端 → 用户实时看到 Agent 的推理文字。

TOOL 节点：LLM 决定调用工具 → 提取 ToolCallSnapshot（工具名 + 参数 + 返回结果）→ 格式化为 Markdown → SSE 推送 → 用户看到「Agent 正在调用 qctask_attribution_infer，参数：{ticketId: xxx}，结果：归因结论为申报价值不符」。
6
Prompt Engineering
提示词工程
WHAT IT IS
Prompt Engineering 是设计和优化「给 LLM 的指令」的技术。LLM 的输出质量高度依赖于你给它的提示词（Prompt）写得好不好。同样一个模型，一个好的 Prompt 能让它精准完成任务，一个差的 Prompt 会让它答非所问。Prompt Engineering 包括：明确任务目标、定义输出格式、指定约束条件、提供示例（Few-shot）、控制推理行为等。
💡 通俗理解
给新员工布置任务，你说「把这个工单处理一下」和你说「请按以下 5 步处理这个工单：第一步查物流轨迹，第二步分析异常原因，第三步生成回复话术……每步完成后必须填写结论」—— 后者显然能得到更好的结果。Prompt Engineering 就是把「布置任务」这件事做到极致。
📂 项目中的 Prompt 设计
invokeSkill() 中构造的系统提示词指令 Agent 按 5 步流水线执行：

① 调用 qctask_get_context 自检当前任务状态
② 依次创建 5 个子任务（qctask_create_sub_task）
③ 每步必须先 start，调用业务工具，再 finish
④ 归因评估不通过时必须重新推理，不能跳过
⑤ 最终必须调用 qctask_finish_main_task 完结

cbaa-prompt 模块按业务域维护独立模板——清关 Agent 的 Prompt 包含 HS Code 分类规范，揽收 Agent 的 Prompt 包含地址解析指令。
7
Multi-Agent 架构
多智能体协作架构
WHAT IT IS
Multi-Agent 是指系统中存在多个 AI Agent，每个 Agent 专注于特定领域或任务，通过协调机制共同完成复杂任务。对比单 Agent（一个 Agent 负责所有事情），Multi-Agent 实现了关注点分离——每个 Agent 只关注自己擅长的事，拥有专属的工具集和 Prompt，互不干扰。
💡 通俗理解
一个医院的运作方式：前台（IntentDetector）接待患者，判断是什么病症（意图分类），然后分诊到对应科室——内科（清关 Agent）、外科（揽收 Agent）、骨科（分拣 Agent）。每个科室的医生（Agent）只关注自己的领域，使用自己的专业设备（工具），不会让骨科医生去看心脏病。这就是 Multi-Agent 的核心思想：专人专事。

为什么不用单 Agent？
工具爆炸 — 6 个业务域加起来有 50+ 个工具，单 Agent 需要从 50 个工具中选择，LLM 容易选错
Prompt 臃肿 — 一个 Prompt 塞下所有业务规则，超过上下文窗口限制，且关键信息被稀释
无法独立优化 — 清关规则改了要影响所有业务域，改一个 prompt 可能破坏另一个域的行为
无法并行扩展 — 新业务域接入需要修改核心 Agent，而非独立新增一个 Agent
📂 项目中的 Multi-Agent 三层架构
第一层 — IntentDetector：LLM 驱动的意图分类器，判断请求属于 CBS/CCS/CFS/CLS/CTS/QA 哪个域
第二层 — MerchantRoutingAgentFactory：根据意图路由到对应业务域的 Agent 实例
第三层 — CbsReactAgentFactory + ThoughtProcessStrategy：业务域 Agent 执行 ReAct 循环，12 种策略适配不同场景
子 Agent 委派：Agent 之间可以通过 SubAgentProvider 互相委派子任务（如清关 Agent 委派给 HS Code 分类子 Agent）
